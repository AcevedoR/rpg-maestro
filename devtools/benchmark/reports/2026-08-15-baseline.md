# Benchmark baseline — 2026-08-15

First full run of the session benchmark harness (`devtools/benchmark/bench.mjs`), across four
environments: dev in-memory, a local prod replica (single instance, true production mode), the
same replica scaled to two instances behind a load balancer, and the real production deployment.
Keep this file as the reference point for future runs — the **Reproducing** section pins the
exact setup.

- **Code under test:** `main` @ `d86ef94` (includes the server-authoritative clock + SSE push
  channel from #116/#119).
- **Harness:** 1 GM + 5 players per session; the GM acts every 2–6 s (60 % change track, 40 %
  pause/resume); players listen on the real SSE stream. 60 s per scenario unless noted.
- **Machine:** Apple M4 Pro, 24 GB, macOS 26.5.1, Node v24.15.0, Docker 29.5.3.

## Results

### Headline comparison (1 session, 1 GM + 5 players, 60 s)

| Environment | PUT p50 | PUT p95 | propagation p50 | propagation p95 | snapshot p95 | fan-out |
|---|---|---|---|---|---|---|
| Dev in-memory (nx `dev-e2e`, host) | 5 ms | 8 ms | 5 ms | 8 ms | 2 ms | 30/30 |
| Prod replica, prod mode, 1 instance | 12 ms | 18 ms | 13 ms | 19 ms | 9 ms | 75/75 |
| Prod replica, 2 instances + LB | 13 ms | 17 ms | 13 ms | 18 ms | 3 ms | 75/75 |
| **Real prod (rpgmaestro.app)** | 234 ms | 321 ms | 223 ms | 318 ms | 69 ms | 75/75 |

*(The dev row is a 15 s smoke run — fewer samples, same magnitudes.)*

### Scale on the multi-instance prod replica (2 instances, shared Redis, 60 s each)

| sessions | players | PUT p95 | propagation p95 | snapshot p95 | events recv/expected | errors | drops |
|---|---|---|---|---|---|---|---|
| 1 | 5 | 17 ms | 18 ms | 3 ms | 75/75 | 0 | 0 |
| 5 | 25 | 12 ms | 12 ms | 5 ms | 390/390 | 0 | 0 |
| 20 | 100 | 11 ms | 12 ms | 4 ms | 1560/1560 | 0 | 0 |

During the 20-session scenario the SSE streams were genuinely split across instances (peak
observed: 74 vs 61 per instance, via each instance's `/health` `openStreams`), so every GM
change crossed Redis pub/sub to reach the other instance's listeners.

### Real prod (rpgmaestro.app, session `Kj2Yh`, 1 session, 60 s)

15 GM actions, 75/75 events, 0 HTTP errors, 0 stream drops over Cloudflare. Pre-run playing
state restored by the harness.

## Findings

1. **The Redis machinery costs ~7–12 ms and does not degrade with load.** Going from pure
   in-memory to the full prod stack (Redis `TIME` clock, Redis session cache, Redis pub/sub
   fan-out) adds single-digit milliseconds. Latency is *flatter at 20 sessions than at 1* —
   at 120 concurrent SSE streams and ~5 GM actions/s the server is nowhere near a limit.
2. **Fan-out was 100 % complete everywhere.** 1560/1560 events delivered in the largest run,
   zero dropped streams in every environment, including through Cloudflare for a full minute
   (the 20 s heartbeat is doing its job).
3. **Real-prod latency is ~95 % network transit.** ~320 ms p95 against rpgmaestro.app vs
   ~18 ms for the same configuration locally: the difference is client↔Cloudflare↔origin
   transit, not server work. Propagation p50 ≈ PUT p50 in every environment — the push
   channel adds virtually nothing on top of the write round trip.
4. **Multi-instance works without Firestore for the playback path.** Session playing-state
   reads go through the Redis-backed `SessionsCache` and changes fan out over Redis pub/sub,
   so a player on instance B follows a session written on instance A. Only `/maestro/*`
   (users/tracks) needed sticky routing, because those live in per-instance in-memory DBs.

## Caveats for future comparisons

- **Firestore is not in the loop.** The replica ran `DATABASE=in-memory`; real prod pays
  Firestore latency on cache misses (mostly session/track setup, not the hot playback path).
- The real-prod run was 1 session from one machine in one network location; its absolute
  numbers mostly measure that path.
- Propagation latency is sequence-matched by the harness (Nth event ↔ Nth GM command) — only
  trustworthy in runs with zero stream drops, which all of these were.
- The 1-session scenarios have few samples (n=15 PUTs); read p95/p99 loosely there.

## Reproducing

### Dev in-memory

```bash
npx nx run rpg-maestro:dev-e2e          # backend on :8099
npm run benchmark -- --all              # 1 / 5 / 20 sessions + comparison table
```

### Local prod replica

```bash
npx nx build rpg-maestro --configuration=production
docker build . -f apps/rpg-maestro/Dockerfile -t rpg-maestro:bench
docker network create bench-net
docker run -d --name bench-redis --network bench-net redis:7-alpine

# True production mode (1 instance, :3100). AUTH_ISSUER must have NO trailing slash —
# the JWT guard appends /.well-known/jwks.json and Auth0 404s the double-slash URL.
docker run -d --name bench-app --network bench-net -p 3100:3000 \
  -e CONFIGURATION_ENV=production -e DATABASE=in-memory -e PORT=3000 \
  -e DEFAULT_AUDIO_FILE_UPLOADER_API_URL=http://localhost:3001/api \
  -e DEFAULT_FRONTEND_DOMAIN=http://localhost:4200 \
  -e AUTH_JWT_AUDIENCE=https://rpgmaestro.app/api \
  -e AUTH_ISSUER=https://dev-8v7iuopd7co3felr.us.auth0.com \
  -e CACHE_REDIS_URL=redis://bench-redis:6379 \
  rpg-maestro:bench
```

Create one session on it with a real Auth0 access token (`POST /maestro/onboard`), then:

```bash
node devtools/benchmark/bench.mjs --base-url http://localhost:3100 \
  --session-id <id> --token <auth0 JWT>
```

For the multi-instance topology, start two more containers from the same image with
`NODE_ENV=dev CONFIGURATION_ENV=dev` (this only re-enables `/test-utils`; nothing else in the
app branches on the env flag, so performance is identical) and
`AUTH_ISSUER=http://bench-app-1:3000/test-utils/fake-idp`, publish them on :3101/:3102, and
front them with a small HTTP load balancer that pipes response streams (SSE): route
`/maestro/*` and `/test-utils/*` sticky to instance 1, round-robin everything else. Then:

```bash
node devtools/benchmark/bench.mjs --base-url <lb url> --all --duration 60
```

Teardown: `docker rm -f bench-app bench-app-1 bench-app-2 bench-redis && docker network rm bench-net`

### Real prod

```bash
node devtools/benchmark/bench.mjs --base-url https://rpgmaestro.app/api \
  --session-id <yourSession> --token <maestro JWT>
```

Prod-safe: the only write is `PUT playing-tracks` and the pre-run state is restored — but
listeners on that session will hear the changes, so use a spare session.
